## Purpose and supported formats

Media securely accepts, organises, processes, describes, restricts, delivers and retires tenant/group-owned **images (JPEG, PNG, WebP, AVIF, HEIC), PDFs, and UTF-8 TXT, CSV and Markdown files**. The owner's `scv` is interpreted as `csv`, the recognised extension. The current **governing catalogue describes images**; PDF/text inclusion is explicitly approved *conceptual expansion*, pending governing reconciliation, not a silently accepted governance change.

No automatic video/audio, executable HTML, office binaries, arbitrary attachments, OCR, PDF authoring, CSV business import, editorial publishing, DRM or comprehensive search service. Unsupported formats are refused, not passed through. PDF, text and image policies differ; a generic attachment is not automatically an image asset.

**Historical design defaults (25 October 2026):** 10 MB standard image intake, 25 MB when entitled, 50 megapixels maximum, WebP widths 480/960/1920, optional cleaned private original. These are reference defaults, **not** verified runtime limits; establish separate PDF page/object and text byte/line ceilings before implementation. HEIC remains in scope, while a strict-permissive decoder path is an unresolved technical investigation.

## Ownership, composition and availability

- **Media owns** file identity, tenant/group ownership and uploader reference, type-specific metadata (image dimensions and alt/decorative status; title/description; credit/licence/consent claims), digest and immutable revisions, processing manifest/status, eligibility, privacy/visibility, holds, quota reservations/usage, lifecycle/tombstones and its persistence/outbox. A rights or consent assertion is recorded, not independently certified.
- **Other authorities:** Storage owns immutable bytes, keys and signed-URL primitives; Identity/Authentication provide trustworthy caller/group context; Authorisation decides permissions; Content Security owns detection evidence; proposed Moderation owns reports/cases/appeals; Publisher owns document publication and backlinks; Privacy/Legal Compliance own applicable policy constraints; Reporting owns reports; Audit owns received evidence; Logging owns diagnostics. Media enforces its own restrictions. Site/public URL possession never constitutes permission.
- **Required composition:** Media-owned database, Storage's provider-neutral Files port, trusted host-provided caller plus server Authorisation (via the IAM Integration façade as applicable); required safety checks are conditional upon exposure and policy. Provider absence, invalid policy or unknown decision fails closed; no direct private inter-capability imports or cyclic dependency. Other services are optional/conditional public ports, not automatic package dependencies. Comply with accepted ADR-0012/0016 and host composition budget.
- **Standalone operation:** with a legitimate host, storage and IAM/policy ports, users can upload/manage permitted files without Publisher, Gallery, Content Editor, commercial processing, Reporting or billing. Configuration/entitlements may supply versioned group allowances; Media enforces them, with conservative configured limits if external limits unavailable. No automatic deletion on subscription downgrade; administrator overrides need authority and evidence.
- **Evidence:** `nuxt-layers/media` exists but at the inspected revision its README says implementation is not built, and there is **no root `CONTRACT.md`**. The root `CONTRACT.md` of Storage verifies `storageFor(consumer,{contentTypes?})` with scoped `signUpload/claim/put/get/head/list/copy/remove/signDownload/usage`; Storage does not impose Media allowances. Publisher's published optional `assets.resolve({siteId,assetIds})` returns an image URL, dimensions or `null`. PDFs/text require a separately agreed typed attachment resolver, not fabricated image dimensions. No actual Media route/function is asserted.

## Native lifecycle and invariants

1. **Prepare:** verify trusted caller/group, size/complexity/type ceilings, rights declarations, entitlement/available quota and permission. Reserve allowance and issue an expiring scoped staging upload. Staged does **not** mean accepted or publicly visible.
2. **Claim/inspect:** verify actual content against declared type, size, SHA-256, tenant key scope, expiry and idempotency key; inspect malformed/truncated files and parser/decompression risks. No duplicate charges, files or committed events on replay.
3. **Process safely:** images use bounded, isolated decoders, remove sensitive EXIF/GPS and generate immutable web variants; cleaned originals are private, opt-in and separately entitled. PDFs require controlled parser, risk checks for embedded scripts/actions/attachments and safe sandboxed preview (otherwise restricted download only); encrypted PDFs refused absent an approved policy. TXT/CSV/MD are bounded UTF-8 and inert previews; never execute HTML or spreadsheet formulae. Keep dangerous originals non-deliverable until qualified.
4. **Decide eligibility:** distinguish pending, processing, held/quarantined, rejected, ready, archived, revoked/removed and erased. Required Content Security evidence must match exact digest/revision/policy version; missing, stale or inconclusive evidence never releases content. Reviewer quarantine access is independently restricted. New content revision/rights/policy can require recheck.
5. **Use/maintain:** authorised picker/preview and current audience-scoped delivery only; stable file ID with immutable byte revision and cache-safe addresses. Metadata editing uses optimistic versions; minimise disclosure of uploader identity, rights and personal data. Archive removes discovery but may preserve existing authorised uses. Reinstatement reruns required checks.
6. **Revoke/delete:** voluntary deletion checks Publisher/document backlinks and holds; blocked operations return scoped reasons. Lawful mandatory takedown/erasure revokes access independently of backlinks, removes originals/derivatives, invalidates caches and preserves only required, non-disclosing evidence/tombstones. Avoid promising instantaneous revocation of already-issued URLs; use short lifetimes and report CDN/purge incompleteness. Restore/backups replay erasure.
7. **Reconcile/recover:** separately report requested, staged, accepted, processing, completed, failed and unknown outcomes; retry safely, reconcile orphan uploads, Storage usage/reserved quota, failed workers, outbox delivery and delayed cache revocation. No impossible distributed exactly-once claim. Scheduled maintenance uses public scheduler/workflow/MQ ports, never makes those services owners.

**Shared context:** caller/tenant/group/site, action/resource, actor assurance, asset/revision/digest, operation/correlation/idempotency, applicable policy version/effective time, delivery audience, result/expiry and evidence provenance. These are logical facts, **not** a mandated universal request DTO. Stable errors should include unauthenticated, forbidden, insufficient-assurance, invalid-input, quota-exceeded, conflict, held, in-use, not-found, pending, unavailable and unsupported-operation.

**Interaction rules:** commands are revision-checked and idempotent where retried; queries indicate freshness, partial availability, provenance and permissions; events follow committed authoritative changes and may be delivered more than once/out of order across consumers. Unknown provider result is not success. Distinguish archived from removed and erased; revoked URLs must not continue serving known content. Stable domain errors should cover unauthenticated, forbidden, insufficient-assurance, validation-failed, quota-exceeded, version-conflict, held, in-use, not-found, pending, unavailable and unsupported-operation. All protected actions are authorised server-side; client picker controls are presentation only.

**Shared context (not a universal request object):** tenant/site/group owner, subject/assurance and authorised resource, asset ID + revision + digest, operation/correlation/idempotency IDs, relevant policy/version/effective time, storage/provider provenance, audience/visibility, completion state and redacted safety evidence. Private storage keys and ephemeral grants are not normal published asset descriptors. Consumers must handle missing, unknown, stale, revoked and partial results without inventing approval.

### Logging, Audit and Reporting contracts

**These three integrations serve different purposes and are not interchangeable.** The existing conceptual Media inputs/outputs, durable outbox and authorisation model remain authoritative. Neither an emitted diagnostic nor an accepted report proves that a Media command succeeded.

| Partner | Media sends (outbound interface) | Media receives (inbound interface) | Responsibility / failure behaviour |
|---|---|---|---|
| **Logging** | Structured technical events: operation type, timestamp, permitted tenant/resource and correlation identifiers, severity, status/error codes, processing latency, parser/Storage failures and retry health; **never** original bytes, sensitive image/PDF/text content, signed URLs, secrets or unnecessary personal data | Optional diagnostic sink availability, delivery/acceptance status and approved operational correlation | Logging owns diagnostic records and sinks; Media owns its own outcome. Logging failure must not grant access, bypass holds or fabricate successful processing. Important audit facts use the durable Media outbox separately |
| **Audit** | Policy-classified, versioned Media-origin assertions: file claimed/ready/revised, permission denial or privileged download as selected by risk, allowance override, quarantine/release, takedown, reinstatement, deletion/erasure and exceptional administrative action; include source-event ID, tenant, actor/assurance where permitted, asset ID/revision/digest, outcome, timestamp and correlation; exclude raw file contents | Evidence intake receipt with accepted/rejected/pending/uncertain status, evidence reference, integrity or coverage alerts and authorised investigation requests | Media remains source of truth for file state and creates durable outbox entries; Audit owns evidential custody, deduplication, tamper evidence and evidence disclosure. A queued or transmitted event is not an accepted Audit record. Record outage/backlog and replay safely, never infer success from missing receipt |
| **Reporting** | Authorised tenant/group/time-scoped asset inventory, type/status, committed/reserved usage and allowance, processing time and failure counts, safe delivery/download aggregates, removal counts, timestamps, revision/event IDs and freshness/completeness indicators | Optional report request/configuration, definition/version, execution status, authorised report link/export, source lineage, refresh age and completeness/partial-result signals | Media owns original asset/usage facts; Reporting owns report definitions, projections, snapshots and exported results. It must recheck disclosure rights, including for aggregate and scheduled reports; stale or partial output must be labelled. Reporting failure does not block normal Media processing |

**Interface direction and composition:** A consumer connects to Media's published queries/events and any approved sink/receipt ports through host composition, not private database tables or direct package cycles. Logging accepts bounded diagnostics; Audit ingests the authoritative committed event class under its own producer/retention policy; Reporting queries or projects Media's authorised source data. Each connection is conditional/optional as a transport, while legally or policy-required evidence creation, preservation and escalation must still fail safely or be durably deferred. Do not confuse log delivery, Audit evidence acceptance and report production. Acknowledgements and report identifiers are not file-authorisation decisions. Define redaction, tenant boundaries, retention, idempotency, backpressure and error taxonomy in the future root Media `CONTRACT.md`.

**Location cooperation:** Location may bind a place or geometry to a typed opaque Media ID and optional revision; it does not copy Media records or raw Storage keys. Media supplies safe thumbnail, variant and original eligibility, including current access/hold/removal status; Location rechecks at display/open. Location owns geo-association/pin lifecycle and cannot authorise Media content. This requirement appears in newer blueprint master; see [Location conceptual record](../location/capability-record.md).

## Security, privacy and operational design

Apply server-side least privilege and cross-tenant isolation to every operation, including direct downloads; no publicly retrievable unapproved uploads. Require bounded file parsing in isolated workers, strict MIME and structural validation, malware/risk gates, CSRF and request-rate controls, temporary credentials, SSRF prevention on any remote import, encrypted storage where required, private-object segregation, bounded cache TTL/purge, data-region controls, retention and backup-erasure replay. Scrub location/device metadata but preserve authorised attribution in Media-owned records. Treat consent/rights declarations as claims, not legal proof; apply UK GDPR, Online Safety Act and children's-data duties only after qualified context assessment. Do not impose indiscriminate private end-to-end-encrypted content scanning. Restrict safety evidence and privileged original access. Document operational health, unknown purge status and independent evidence capture without leaking signed addresses or file content.

## Applicable standards and design assurance

**Status:** Verified standards reference baseline for the owner-approved Media concept; no certification, implementation conformity, legal conclusion or additional user decision is claimed. Apply standards proportionately to the operations and file types supported; maintain a versioned compliance/acceptance mapping in the eventual public `CONTRACT.md`.

### Essential baseline
- **OWASP ASVS 5.0**, especially file handling/upload, access control, validation and secure output; the OWASP File Upload Cheat Sheet is supplementary implementation guidance, not an ISO standard. Apply ASVS L2, escalating security-critical operations where the risk assessment warrants L3. https://github.com/OWASP/ASVS/blob/master/5.0/en/0x14-V5-File-Handling.md ; https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html
- **W3C WCAG 2.2 AA** for optional Media screens and accessible image/preview presentation; WAI image tutorials guide functional versus decorative alternatives and context-sensitive alt text. Media records accessibility information but the publishing context determines the final image alternative. https://www.w3.org/TR/WCAG22/ ; https://www.w3.org/WAI/tutorials/images/
- **ISO/IEC 27001:2022 and 27002:2022** security-management/control references; **ISO/IEC 27701:2025** for privacy management; **ISO/IEC 27017:2026** for cloud controls. These guide platform assurance; the Media package cannot itself assert organisational certification. https://committee.iso.org/management-system-standards-list.html ; https://www.iso.org/standard/27017
- **IETF RFC 9110 (HTTP semantics)** and **RFC 6266 (Content-Disposition)**: correct content types, cache/conditional request behaviour, safe attachment naming/download, expiry and revocation expectations. https://www.rfc-editor.org/info/rfc9110/ ; https://www.rfc-editor.org/info/rfc6266/
- **Applicable UK GDPR / DPA 2018 as amended** and ICO privacy-by-design guidance; use UK NCSC cloud security principles for provider configuration, secrets, isolation and recovery. Apply qualified Legal Compliance assessment for actual statutory duties. https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/accountability-and-governance/guide-to-accountability-and-governance/data-protection-by-design-and-by-default/ ; https://www.ncsc.gov.uk/collection/cloud/the-cloud-security-principles

### File-type technical profiles
- **Images:** JPEG ISO/IEC 10918 family; W3C PNG Third Edition (Recommendation, 2025) and ISO/IEC 15948; WebP format specification; AVIF by AOMedia and ISO/IEC 23000-22:2025 (MIAF); HEIF ISO/IEC 23008-12:2025. Validate actual container/decoder support and constrained resources rather than assume all optional features are safe. https://www.w3.org/TR/png-3/ ; https://aomediacodec.github.io/av1-avif/latest-approved.html ; https://www.iso.org/standard/87576.html ; https://www.iso.org/standard/89035.html
- **PDF:** ISO 32000-2 (PDF 2.0); ISO 14289-1 (PDF/UA-1) and ISO 14289-2:2024 (PDF/UA-2) guide accessible PDFs; ISO 19005-4:2020 (PDF/A-4) guides optional preservation. Safe parsing and accessibility are independent decisions: do not equate malware-free with accessible, or require all historic PDFs to be PDF/UA without an applicable policy. https://pdfa.org/pdf-standards/ ; https://pdfa.org/iso-status/
- **Text:** Unicode/UTF-8 (RFC 3629), CSV RFC 4180 with optional W3C CSV on the Web metadata, Markdown `text/markdown` RFC 7763 and a documented CommonMark dialect where parsing is offered. Render uploaded TXT/CSV/MD as inert data; escape markup and guard CSV formula injection where exported into spreadsheet software. https://www.rfc-editor.org/info/rfc4180/ ; https://www.w3.org/TR/tabular-metadata/ ; https://www.rfc-editor.org/info/rfc7763/

### Optional specialist interoperability
- **IPTC Photo Metadata Standard 2025.1** for captions, attribution, creators and rights metadata; do not preserve dangerous/private embedded EXIF/GPS merely to support IPTC. Use vetted fields in Media-owned records. https://iptc.org/standards/photo-metadata/iptc-standard/
- **C2PA Content Credentials** for optional cryptographically verifiable provenance/alteration history; do not imply that a valid signature establishes truth, rights or permission. Sanitisation and derivative creation may invalidate embedded credentials: preserve permitted provenance separately and disclose transformations. https://spec.c2pa.org/
- **W3C PROV-DM** for interoperable provenance of source, derivative and enforcement decisions where cross-system exchange warrants it. https://www.w3.org/TR/prov-dm/
- **EN 301 549 / UK public-sector accessibility requirements** where a deploying organisation falls within their scope; determine the applicable edition/obligations with Legal Compliance instead of making universal claims. W3C WCAG 2.2 AA remains the platform design baseline.

**Acceptance mapping:** demonstrate valid/invalid format detection; isolation and resource-bounded parsing; safe PDF and inert text previews; alt/credit/rights and scoped access; immutable revisions, HTTP delivery/caching/revocation; tenant boundaries; retention and erasure; privacy/metadata stripping; provenance/derivative handling; accessible GUI and document-status indication. Distinguish mandatory governing controls, external standard guidance, applicable law and optional interoperability. Updates to standards must be reviewed for impact rather than silently changing supported file behaviour.

### Rejected/deferred selection and dependency cautions

- **Sharp/libvips**: Sharp's Apache-2.0 licence does not make its LGPL libvips/bundled native libraries permissively licensed. LGPL can permit commercial use with conditions, but is **outside the requested strict permissive-only selection policy** unless separately approved.
- **libheif**: current LGPL-3-or-later; HEIC support remains an **approved conceptual format with an unresolved compliant codec/implementation path**. No silent removal of user-approved HEIC from scope and no claim a strict-permissive HEIC decoder has been found.
- **imgproxy**: although the GitHub community code is open-source, premium proprietary Pro functionality is sold separately; exclude under the user's complete-flagship-source requirement. Also depends on libvips.
- **Ghostscript, MuPDF and Poppler**, where distributed under AGPL/GPL, are excluded from the strict-permissive baseline; do not accidentally pull them into ImageMagick delegates or PDF preview pipelines.
- **veraPDF** is dual MPL-2.0/GPL-3.0; while source is public and commercial use can be permitted, MPL is file-level copyleft and is *not* in the strict permissive shortlist. Consider only under an explicit expanded licence policy and if PDF/UA or PDF/A validation is needed.
- **pdf-lib**: MIT but last widely adopted upstream stable version is old; do not select it as the primary security-sensitive PDF backend without independent maintenance/security review.
- **Closed-source/cloud-only, open-core and legacy unmaintained variants** are rejected even if named as common substitutes. No third-party API dependency should be required for native Media operation.

**Proposed minimal toolchain:** file-type + hardened ImageMagick with audited permissive-only delegates/codecs for image processing; PDF.js for presentation and qpdf for PDF inspection; csv-parse/csv-stringify for CSV; markdown-it and optional DOMPurify for inert previews. Use native UTF-8 validation for TXT. Use Storage's existing public contract for bytes and Content Security's for detection. Introduce exifr, YARA-X or C2PA only when an actual requirement justifies the additional dependency. A policy-approved HEIC path and PDF safe-sanitisation approach remain implementation investigations. Before acceptance, prove format handling, isolation/time/memory limits, license chain and SBOM, resilience, security and Nuxt host composition in user/CI-controlled tests.
