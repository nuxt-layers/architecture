## 1. Purpose, ownership and boundaries

**Theme Manager advisory reciprocity (23 November 2026; [Theme Manager PR #142](../../presentation/theme-manager/presentation-record.md)):** Reporting may consume authorised Theme Manager public read models or committed change facts (scoped summary/status/version, validated publication provenance and lawful aggregates) to produce reports, under independent source permissions and freshness declarations. Reporting returns report run/availability/export status; it cannot edit themes, read private Theme Manager tables or substitute audit/log records for authoritative theme state. No published Reporting connector is asserted. 


Reporting lets authorised users and services **define, run, view, refresh, schedule, export and distribute reports** built from information supplied by other capabilities. It provides reusable reporting without requiring each business capability to implement its own analytical service.

**Reporting owns:** report definitions, approved measures and parameters, revisions and reusable templates; report execution and refresh state; derived datasets, scoped snapshots and visualisation descriptions; source binding, quality, provenance and correction information; report-specific schedules, delivery plans, approved sharing scope and delivery attempts; generated report artefact references, expiry, revocation and Reporting's own committed lifecycle events/outbox.

**Reporting does not own:** source transactions or corrections; identities, permissions or privacy/legal decisions; authoritative accounting, payments, attendance, qualifications, production, employment, security findings or operational incidents; Audit evidence, Logging records or Observability measurements; Storage bytes, Export rendering or transport-provider state. A report **describes** qualified source facts; it does not approve, certify, post, fulfil or change them. Other capabilities remain operational without Reporting.

Reporting owns its state and stores behind its own persistence port. Applications provide infrastructure, caller/access decisions and configuration through public composition contracts. Neither Reporting nor its connectors may read another capability's private tables or code. All public-contract and Nuxt-extension dependencies must be declared, directional and acyclic.

## 2. Native service, release scope and lifecycle

**REP-01 — approved first release:** on-demand, single-source reports based on explicitly authorised projections. Supply curated built-in templates and safe parameterised counts, totals, grouped measures, trends, tables and read-only charts. Reject arbitrary SQL, unrestricted formulas, user-authored cross-source joins and cross-tenant benchmarking. Later cross-source reconciliations require reviewed common keys, units, periods, authority, corrections and completeness.

**Lifecycle:** `draft → validated → published/active → revised/withdrawn → retired` for report definitions; `requested → accepted → running → completed/partial/failed/cancelled → invalidated/expired` for executions and derived results. `unknown` records uncertainty where completion or source outcome cannot be established; neither a queued job nor a provider timeout proves failure or success. Schedules and distribution plans have separate `draft/pending-review/approved/active/paused/expired/revoked` states, with per-attempt transport outcomes.

A normal execution verifies scope and permissions, reads qualified public source data, checks units/time windows and coverage, computes allowed measures, enforces privacy/disclosure restrictions and returns a versioned result with provenance. Corrections and replay-safe source events invalidate affected derived data and permit explicit refresh. Preserve the distinction between results *as observed then* and *as corrected now*; label unavailable historical evidence rather than reconstructing unsupported certainty.

**Minimum independent mode:** manual authorised definition, execution, results and meaningful failures; no Scheduler, Workflow, export renderer, Mailer, external BI engine or GUI required. Expensive requests may run asynchronously. Missing required source, store or access decision refuses the affected operation; optional service absence disables only its dependent feature.

**Time & Attendance conceptual source (TA-01–TA-06 owner-approved; PR #143):** provides authorised read models of submitted/approved/disputed/adjusted work intervals, actual hours, break durations, exceptions, Task effort reconciliation references, units, tenant/subject scope, effective period, source revision, provenance, correction history and freshness/completeness. Committed revision-change events may request invalidation/refresh; Reporting must reauthorise/re-query rather than treat the event as report data. Reporting returns source-qualified totals, reports, partial/unknown results, snapshots and exports, never changes attendance approvals or converts presence into payable hours. Missing Reporting does not prevent attendance recording. No shipped integration is asserted.

## 3. Idealised public input contract

These are **logical business-level interfaces**, not verified exported functions, REST routes or universal request types. Each input identifies its trusted supplier and authority.

| Input | Supplier and content | Validation and absence |
|---|---|---|
| Caller, access and report commands | Trusted host/IAM caller and Authorisation decision; permitted user requests to define, publish, run, refresh, cancel, view, export, schedule, share or revoke | Server-side tenant/resource/action checks, assurance, version/idempotency, safe parameters; unknown or denied permission fails closed |
| Report and policy configuration | Authorised editor/host/Configuration: definition revision, approved source, fields, calculation, period, purpose, allowed viewers, retention, channel and enabled features | Reject unknown field, unsafe expression, scope, mixed currency/unit, unreviewed join or contradictory policy; report definition owned by Reporting |
| Source read models | Each business capability: purpose-scoped facts, source ID/revision, effective/observation/as-of time, units, denominator, provenance, completeness, freshness, omissions and corrections | Source remains authoritative. Missing/stale/conflicting data becomes qualified partial/unknown/unavailable, **never silently zero** |
| Source change notifications | Source-owner committed event/outbox via Message Queue: event ID, source revision and affected scope | Optional refresh optimisation, idempotent with duplicate/out-of-order delivery; re-query authoritative source before recomputation |
| Privacy, legal and time context | Privacy/Legal Compliance restrictions, lawful purpose/consent where applicable, retention/hold/transfer, Clock time-zone and period semantics | Required when relevant; uncertainty or invalid disclosure blocks unsafe output |
| Job and approval inputs | Scheduler trigger; Workflow or independent authorised approval; permitted recipient, schedule, purpose, channel and expiry | Conditional to scheduling/distribution; a trigger or approval never grants source access independently |
| Output infrastructure | Storage file port, Export safe-tree rendering, Notifications/Mailer/Integrations provider outcomes | Conditional on export/delivery; retain failed/unknown state, never invent a file or confirmed receipt |

## 4. Idealised public output contract

| Output | Meaning and authorised consumer |
|---|---|
| Catalogue and definition query | Visible templates and versions, parameters, measures, source/owner, purpose, publication state and available actions for authorised host/UI/users |
| Definition/management command outcome | Accepted, refused or revised definition; ID/revision, validation issues, policy/version and safe error reference; **accepted does not mean executed** |
| Execution, refresh and schedule status | Run/plan reference, queued/running/completed/partial/failed/unknown/cancelled/invalidated/expired, grounded progress, retry and correction/reconciliation state |
| Qualified result and visualisation | Permitted tables, measures and chart descriptions, units, denominator/population, filters, source lineage/revisions, cutoff/as-of/effective times, freshness, completeness and explicit suppression/uncertainty |
| Historical snapshot and export | Authorised reference/format, safe artefact status, expiry, retrieval scope and revocation; Storage owns bytes, Export Library renders approved rich text, neither grants access |
| Recipient-specific distribution outcome | Approved plan/recipient and attempt reference, queued/accepted/sent/failed/unknown or evidence-qualified delivered status. Provider acceptance is not recipient reading |
| Committed Reporting lifecycle events | Minimal tenant-scoped `definition.changed`, `run.completed/partial/failed/invalidated`, `artifact.revoked/expired`, `distribution.status-changed`, with version, event ID, source ref and effective time; no unrestricted result rows |
| Technical errors and operational status | Safe versioned error code, category, `messageKey`, correlation and qualified retry hint, using Error Normalisation; no stack, secrets or sensitive source payload |

**Commands** check permission, expected revision, validation and idempotency; distinguish request acceptance from completed effect. **Queries** independently authorise catalogue, filters, source values, aggregation, drill-down, snapshot, download and recipient. **Events** follow committed Reporting-owned changes through its durable outbox; consumers tolerate replay/reordering. Exactly-once distributed delivery is not promised. Version breaking changes explicitly; do not leak private persistence types.

## 5. Scheduled distribution and sensitive disclosure — REP-02 approved

Scheduling computation **does not** authorise delivery. The approved sequence is:

1. **Plan:** authorised editor requests a revision-bound report plan, cadence, named or dynamically resolved recipients, purpose, channel, source/tenant scope and expiry. No send yet.
2. **Review:** classify actual source sensitivity, not just a supplied label. Self-only low-risk in-app viewing can be self-service; sensitive or external distribution needs a different authorised reviewer. An applicant cannot self-approve a high-risk plan. Bind approval to definition revision, parameter/scope, permitted recipient rule, purpose, channel and expiry.
3. **Activate:** Reporting stores approved plan state and registers an opaque trigger with Scheduler; the Scheduler never receives report rows or decides disclosure.
4. **Generate:** each trigger runs a fresh, authorised report; resolve group membership into eligible recipients at send time. Changed risk, revision, recipient scope or purpose suspends the affected plan pending renewed approval.
5. **Pre-dispatch:** recheck source/current access, privacy/retention/legal restrictions, group/recipient permission and suppression separately **for each recipient and send**. Fail closed on uncertain entitlement.
6. **Deliver:** favour recipient-bound, expiring in-app download links over unrestricted attachments. Notifications/Mailer/Integrations owns transport; Reporting tracks stable plan/occurrence idempotency, per-recipient attempt and `queued/accepted/sent/failed/unknown/evidence-confirmed-delivered` status. Reconcile unknown provider outcomes before retrying when possible; do not double-send on replay.
7. **Withdraw/recover:** expiry, revocation or changed permissions prevents future sends and disables controllable links/queued work. Audit receives risk-selected accountable approval/disclosure facts; Logging receives scrubbed diagnostics. Copies already downloaded or externally forwarded cannot be technically recalled.

**Operational policy still to define:** sensitivity thresholds, precise review delegation and exception controls, approval maximum life, dynamic-group change criteria, attachment/channel rules and retry budget. These must respect the approved independent approval, recipient isolation, expiry and fail-closed defaults; they are configuration/implementation matters, not permission to weaken the design.

## 6. Other approved policies

**REP-03 — retention and historical integrity.** Store versioned definitions separately from derived caches, snapshots, export bytes and Audit evidence. Minimise snapshot/file lifetime by approved purpose and source/privacy/legal constraints; valid legal holds can require restricted preservation. Erasure may invalidate or remove derived results while retaining only permitted minimal source revisions, run status and proof references. Never retain personal payloads indefinitely merely to reproduce old reports. Mark unavailable history truthfully.

**REP-04 — external BI and providers.** Native Reporting works without external platforms. External BI, warehouse or connector use is optional, tenant/purpose-approved and **off by default**. Use provider-neutral public ports, scoped credentials, minimised datasets and verified locality, transfer basis, processor/security terms, provider cost, withdrawal and deletion/reconciliation. External data never replaces source ownership. The host decides infrastructure and deployment.

**REP-05 — templates and benchmarking.** Distinguish tenant report editor, tenant-wide publisher, viewer, privileged operator and independent distribution approver. A platform-wide curated template does not grant access to customer data. No default cross-tenant benchmarking; later optional benchmarking requires a separate justified purpose, participating-tenant permission, strong aggregation/non-inference and source/privacy/legal approval. Tenant administrator status alone is not a blanket right to restricted individual reports.

**Privacy and security baseline.** Enforce OWASP ASVS 5 Level 2 (L3 for relevant high-risk operations), server-side Authorisation, tenant isolation, purpose and data minimisation, anti-injection/approved measure grammar, query and cost budgets, signed limited-time files, credentials and secret isolation, sensitive-group differencing protection, and source-revocation checks on saved outputs. A group total or shared export can still reveal individuals; aggregation is not automatically anonymisation. Legal Compliance/Privacy provide applicable constraints; Reporting enforces them and cannot self-certify statutory compliance. All storage caused by an eventual implementation must be documented in its `STORAGE-REGISTER.md`.

**Availability and performance.** Bounded/paginated reads, asynchronously processed large requests, source query quotas and cost limits, scoped versioned derived cache with expiry, refresh lag/coverage indicators and isolated analytic work should prevent reporting from disrupting source transactions. Provider outages or missing data remain explicit. An optional specialised analytical engine must not become another source of truth or an excuse to query private business schemas.

**Task reporting source reciprocity (TASK-01–14 owner-approved, 23 November 2026):** Task publishes resource/tenant/purpose-authorised, revisioned task status, planned/actual dates, hierarchy/dependencies, blocker/resource-need summaries, self-reported versus independently verified completion, bounded evidence metadata, corrections and unique event IDs, with source as-of, provenance, denominators and completeness. Reporting independently consumes through Task's public query/event surfaces, not Task storage or Logging counters, and returns authorised report definition, run/reference/refresh status, backlog/overdue/lead-time/throughput/resource-demand analysis, qualified trends, exports, revision/cutoff/freshness and partial/unknown coverage. Reports may not certify Task completion, allocate people/assets, approve Project milestones, infer Accounting costs or bypass source authorisation. Task's native work continues if Reporting is unavailable. See [Task canonical contract](../task/capability-record.md#error-normalisation-logging-audit-and-reporting--public-inputoutput-boundaries-23-november-2026).

**[Page Builder](../../presentation/page-builder/presentation-record.md) reciprocal interface:** PB-20/21 approved: Page Builder supplies authorised bounded composition, component/version usage, validation/accessibility and template compatibility projections with scope/revision/as-of/coverage. Reporting returns derived reports with freshness/coverage and explicit gaps. Publisher owns inventory/lifecycle facts, Observability performance metrics, Audit evidence; use their public reads separately. No raw logs/drafts, visitor profiling or automatic accessibility conformance claim.

**Error Normalisation, Logging and Audit — distinct responsibilities:** [Error Normalisation](../../libraries/error-normalisation/stateless-library-record.md) is a pure stateless library. Reporting passes a known exception/outcome, mapping, correlation and disclosure profile and receives a safe stable code, category, `messageKey`, bounded public/diagnostic projection and advisory retry classification; it cannot decide whether a timed-out business transaction committed. [Logging](../../services/logging/services-record.md) receives separately scrubbed technical run/export/delivery diagnostics and returns its own accepted/rejected/uncertain intake, scoped records and loss/sink health, **not business success or Audit custody**. Reporting may analyse permitted Logging/Audit read models as sources, retaining their uncertainty, but **owns only derived reporting**, not logs or evidence. If mandatory Audit evidence is unavailable, follow applicable hold/fail-closed policy. A normalised error or log count cannot prove report failure, successful payment or legal compliance.

**Scheduler reciprocity (owner-approved SCH-01–08, 23 November 2026):** The Scheduler's authorised public read models or committed event references feed Reporting aggregates; Reporting returns optional derived operational reporting and cannot modify Scheduler, turn missing data into zero, infer completed business effects or replace Logging/Audit evidence. Scheduler stays operational if Reporting is unavailable. See [Scheduler canonical public contract](../../services/scheduler/services-record.md#idealised-public-contract) and [diagnostics/evidence boundaries](../../services/scheduler/services-record.md#error-normalisation-logging-audit-and-reporting). **Dependency rule:** Composed directional ports, source-owned events and public reads avoid package cycles. Reporting's absence must never block Identity, Booking, Accounting, Scheduler or other source owners' native operations. A source can offer a deep link to Reporting without importing its implementation.

## 10. Conceptual acceptance and completion

| Scenario | Required outcome |
|---|---|
| Valid, authorised single-source query | Accurate metrics, unit/denominator, source revision, provenance/cutoff and permitted completed result |
| Missing period, timeout, unknown provider or partial source | Named incomplete/unknown state and source gap; no fabricated zero, delivery or rollback |
| Invalid formula, field, currency or window | Safe stable error with no unsafe query executed |
