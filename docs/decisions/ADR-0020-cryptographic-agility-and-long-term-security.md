# ADR-0020 — Cryptographic agility and long-term security

**Status:** Proposed for governing adoption (owner approved direction 27 November 2026; adoption on reviewed merge).

## Context

Long-lived confidential data faces harvest-now-decrypt-later exposure. Quantum advances, improved classical algorithms and AI-assisted attack automation require planned migration, not claims of mathematical invulnerability. Existing ASVS, privacy, ownership and provider-neutrality requirements remain in force.

## Decision

1. Maintain an inventory of cryptographic uses, algorithms, protocols, key owners, data lifetimes, dependencies, provider constraints, and migration deadlines. Risk-prioritise long-lived confidentiality, signing and recovery. Version algorithm identifiers and key envelopes; support controlled rotation, revocation, re-encryption, verification of historical signatures and compromise recovery without silent downgrade.
2. Prefer maintained native Node.js/Web Crypto/OpenSSL or established protocol implementations. Assess standardised hybrid classical/post-quantum key establishment and ML-KEM (FIPS 203); assess ML-DSA (FIPS 204) and SLH-DSA (FIPS 205) for signatures where ecosystem interoperability permits. Use reviewed authenticated encryption (e.g. AES-256-GCM with safe nonce management), appropriate hash/KDF profiles and OS-backed CSPRNG. Do not invent cryptographic algorithms, hand-roll handshakes, or silently weaken mandatory policy. Legacy compatibility requires explicit risk acceptance, expiration and migration plan.
3. Assess each trust boundary (TLS, database, SSH, object storage, Temporal, credentials, federation, integrations, signed images/documents and backups). Record actual negotiated protocols and provider limitations. A Node crypto API alone does not prove proxy or external provider PQC support; use standardised interoperable implementations and verify downgrade/failure handling.
4. High-value key recovery may use reviewed threshold secret sharing with genuinely independent custodians, authenticated share transport, controlled reconstruction and tested loss/compromise procedures. Shamir secrecy below threshold does not protect the underlying encrypted data if its cipher fails. P versus NP remains unresolved; no platform-wide P=NP-proof claim. One-time pads are not a platform encryption mechanism; CSPRNG output is not a proof of true independent randomness, and XOR alone provides no integrity.
5. Prefer native primitives; evaluate @noble/post-quantum, @noble/ciphers, @noble/hashes, @noble/curves and shamir-secret-sharing only for justified gaps. Alternatives @quxtech/pqc-crypto, @digital-defiance/secrets-ts and liboqs require separate release, dependency, licence, audit and interoperability review. Neither JS/JIT, WASM nor HSM automatically guarantees constant-time execution. Assess side channels, memory exposure, entropy and key custody. Hardware-backed custody (PKCS#11 or equivalent) is risk-dependent; no hardware purchase is a local acceptance prerequisite.
6. Prove known-answer tests, interoperability, key rotation/recovery, downgrade resistance, failure handling, resource budgets, supply-chain integrity and negative isolation locally. Equivalent production security policies are mandatory; local failure blocks release, local success does not waive environment-specific verification. Assess automated abuse, AI-assisted attacks and resource exhaustion without treating AI as proof that cryptography is broken.
7. Infrastructure provisions secure facilities and reports qualified readiness; data/credential owners retain key purpose, access, lifecycle and data migration authority. No generic crypto service or mandatory new package is introduced. Zero additional local expenditure; defer paid production provisioning until owner-approved local MVP acceptance.

## Evidence and adoption

Owners document their cryptographic profiles and migration gates; Infrastructure documents supported protocol/provider combinations and local/production differences. Exact versions, profiles, assurance thresholds and migration deadlines are engineering decisions requiring evidence. No FIPS module validation, universal PQC availability or compliance is claimed.
