# Infrastructure — canonical infrastructure specification

**Classification:** Infrastructure (CLS-15, approved 24 November 2026). INF-01–05 approved on 18 November 2026, with INF-01/02/05 refinements retained. Conceptual specification only; implementation and operational acceptance are independent.

## Purpose, ownership and exclusions

The Infrastructure artefact defines the reproducible hosting-environment build standard, Docker/image/Compose definitions, server installation, verification, upgrade and recovery tooling for development, acceptance and production. The authoritative implementation repository is `nuxt-layers/infrastructure`. It is not a compulsory Nuxt Layer or independent business-data service. Optional host-operated management and status interfaces complement the deployment definitions.

Infrastructure/host owns provisioned providers, scoped connections/credentials, network ingress, TLS, resource readiness, backup/restore infrastructure, trusted UTC synchronisation and operational recovery. Each stateful owner retains schema, migrations, transactions, business records, authorisation, data-level retention and outbox. Site Hosting owns verified site bindings; Clock owns temporal semantics; Configuration owns approved setting values, not operational permission or applied state. Never treat a provider acknowledgement as verified readiness.

## Operational lifecycle and interfaces

Define approved desired environment → validate versions, scope, provider and prerequisites → provision and verify applied resources → expose qualified readiness → monitor → reconcile failures → upgrade or restore → retire securely. Separate desired, pending, applied, failed, degraded and unknown outcomes. Required unsafe or unavailable providers fail closed. Preserve operator approval and rollback/recovery evidence; never grant broad cross-owner data access. Use verified UTC upstream with holdover/quality evidence; Clock interprets timestamps separately.

| Input | Qualified output |
|---|---|
| Owner requirements and supported provider/version/region constraints | Scoped connection/resource readiness and compatibility evidence |
| Authorised installation/change/backup/restore request | Desired/applied/pending/failed/unknown operation and attributable evidence |
| Verified host UTC source and synchronisation observations | Trusted host instant and separate quality, holdover and recovery status |
| Provider observations and diagnostics | Minimised operational health, loss/degradation and recovery state |
| Source-owned recovery/migration requirements | Resource-level backup/restore verification, not business outcome or migration authority |

The detailed approved installation/operational contracts and reciprocal boundaries below remain authoritative within this blueprint. Interactive management and status are restricted to explicitly authorised host super-administrators (INF-02); service-to-service scoped readiness ports are not a general operator console. No arbitrary SQL or global business CRUD.

## Conceptual acceptance

Verify reproducible installation, scoped resource isolation and secrets, version compatibility, absent-provider refusal, independent database ownership, authorised privileged operations, qualified UTC degradation/recovery, backup and verified restoration, matching ingress/TLS evidence, redacted telemetry and accessible optional operator views. Use documented host procedures and existing providers; no implementation/test execution is claimed.

## Persistence — approved provider and operations boundary (22 November 2026)

**Owner-approved PERS-01–03 and supplementary controls, conceptual only; no implemented port assumed.** [Persistence architectural reference](../../architecture/persistence.md) is now the single blueprint location for cross-cutting storage ownership and the distributed input/output contracts. Persistence is **not** an independent capability or generic service (accepted ADR-0002/0006): each stateful owner retains its schema, migrations, transactions, tenant-scoped query/command checks, authoritative state and durable outbox. Infrastructure/host owns provider selection, secure connections/credentials/TLS, deployment resources, backup/restore infrastructure and qualified operational readiness, not another capability's business data or schema decisions. Owners publish provider requirements and compatibility/erasure procedures; the host supplies scoped resources and reports verified applied state, backup/restore results, failure and recovery status. Required unavailable/unsafe resources fail closed; avoid privileged cross-schema queries and common business record CRUD. **GUI and test-host integration:** [the current approved Persistence presentation specification](../../architecture/persistence.md#gui-and-test-host-integration) confirms **no independent Persistence sidebar or dashboard**. The representative `nuxt-layers-test/application-test-template` uses a host-owned collapsible sidebar with `/admin` and Theme Manager at `/theme-manager`; the host could add a single **Infrastructure** item and dashboard (illustrative `/admin/infrastructure`, not an implemented route). Prefer qualified read-only views of provider/database status, per-capability migration compatibility, backup/restore verification, and scoped operational warnings. Optional diagnostics link to Logging/Observability/Audit through their own public contracts; highly privileged maintenance controls require fresh authorisation, separate approval where required, explicit outcome states and attributable Audit evidence. Every menu item, deep link, API and export is restricted to **explicitly authorised host super-administrators** under approved INF-02; no tenant admins, arbitrary SQL, direct business-table browsing, global migration, cross-owner data erasure or separate Persistence GUI. Host owns navigation; Infrastructure owns operator presentation/status; Theme Manager owns semantic styles; require WCAG 2.2 AA, i18n, mobile/keyboard navigation and truthful degraded/unknown evidence. The template's unauthenticated Theme Manager test mode is **local-only** and never a production IAM substitute. The [approved external standards mapping](../../architecture/persistence.md#established-standards-and-regulatory-guidance--approved-conceptual-mapping-22-november-2026) guides Infrastructure's provider trust, least-privilege database roles and credentials, encryption, backup/restore drills and sanitisation (ISO/IEC 27001/27002/27040/27017, ISO 22301, NCSC Cloud Security Principles, NIST SP 800-53/800-88); source owners retain data-level controls and Privacy/Legal Compliance determine legal applicability. No certification, legal compliance or implemented API is asserted. **Approved fully open-source technology boundary:** the [Persistence technology selection](../../architecture/persistence.md#complete-source-commercially-permissive-open-source-technology-selection-22-november-2026) selects permissively licensed PostgreSQL with default `pg`-compatible Node driver; Infrastructure may operate PgBouncer (ISC) and pgBackRest (MIT) when justified, while Kysely and node-pg-migrate are source-owner-local optional tools. Apache AGE, pgvector, pg_cron and PGMQ remain conditional to graph, Search, maintenance and Message Queue respectively. Do not introduce a global ORM or mandatory shared Persistence SDK. Require exact source/version/licence, transitive dependencies, PostgreSQL 18 compatibility, and verified restore and pooling semantics before deployment; PostgreSQL 19 is not an automatic migration. This is not a new runtime API or an approval to merge implementation changes.

## Cross-capability note — Clock source synchronisation and operator GUI (17 November 2026)

**Conceptual Clock direction owner-agreed; Infrastructure review incomplete.** [Clock](../../services/clock/services-record.md#owner-approval-and-ntp-governance-clarification-17-november-2026) retains the typed synchronous `now()` consumer port and never becomes an NTP client/daemon. Infrastructure operates OS time synchronisation, provider reachability, NTS authentication where supported, fallback/holdover and applied-policy status; Configuration may supply a privileged approved provider policy. A shared host clock cannot be changed by tenant or Profile preferences. ## Reciprocal note — Approved host UTC authority and synchronisation boundary (17 November 2026)

**Clock ownership approved; Infrastructure integration remains conceptual.** See [Clock's UTC-source classification](../../services/clock/services-record.md#approved-utc-source-classification-and-geographic-selection-17-november-2026). Infrastructure owns selecting/applying NTP/NTS policy to OS synchronisers, source authentication and reachability, compatible leap-second/smear handling, fallback/holdover, failure recovery and applied policy revision. Approved national authority candidates include UK NPL's UTC(NPL) public internet service, US NIST; Cloudflare offers NTS; regional volunteer NTP Pool DNS such as `uk.pool.ntp.org` and `europe.pool.ntp.org` are not national laboratories. Confirm live endpoints, permitted use and security properties before any production selection. Host location and assurance—not tenant civil time zone—govern source choice. The optional **Time synchronisation** operator screen belongs to Infrastructure/host presentation, with safe settings from Configuration, health/history from Observability and server-side operator access checks. Clock's `now()` stays a host-supplied synchronous port, not a per-request NTP fetch.

## Reciprocal invariant — verified UTC upstream, separate regional zone interpretation (17 November 2026)

**Owner approved:** Infrastructure must apply a governed, verified and approved internet UTC time source to the host synchronisation service. A regionally located NTP server is selected for trust, resilience and network suitability, *not* to supply a particular local time zone. [Clock](../../services/clock/services-record.md#approved-invariant--utc-authority-and-local-civil-time-17-november-2026) derives GMT/BST and other regional civil times by applying explicit IANA zone and daylight-saving rules to the host-supplied trusted instant. Infrastructure must surface failure or insufficient assurance rather than assert a source is verified solely because it is listed in a candidate catalogue; exact verification/holdover policy remains technical design.

## Reciprocal note — approved CLK-03/CLK-04 reliability boundaries (17 November 2026)

**Clock conceptual decisions approved; Infrastructure implementation not established.** [Clock's final completeness review](../../services/clock/services-record.md#final-completeness-review--eight-concerns-resolved-17-november-2026) requires Infrastructure to provide approved verified UTC synchronisation and a clearly evidenced, versioned source-quality status to authorised host consumers: applied versus desired source, authentication result, sync freshness, offset/uncertainty, degraded/holdover/unavailable state, policy version, failure and recovery. An NTP hostname or successful current-time read alone cannot certify trust. Infrastructure owns step/slew corrections, leap-smear compatibility, bounded holdover and recovery mechanics; no tenant source selection. Infrastructure does not own business expiry decisions, monotonic timeout policies or Clock's time-zone conversion. Exact assurance thresholds, synchroniser and host interface remain technical design.

## Owner clarification — Infrastructure's original and primary purpose (18 November 2026)

**Approved refinement of INF-01:** The `nuxt-layers/infrastructure` repository is the authoritative source for the **hosting-environment build standard**, its Docker/image/Compose configurations and server installation, verification, upgrade and recovery scripts. It defines reproducible development/acceptance and production deployment requirements, provider configuration and operational acceptance instructions. This is not merely a host-owned status service and does not require a standalone Nuxt Layer. The operational change/readiness/status/time/backup interfaces and optional operator GUI are **additional, complementary responsibilities**. Preserve a self-contained documented installation/deployment interface and an independently recoverable script-based bootstrap; optional operational APIs must never become prerequisites for server recovery. See amended conceptual review (former review: infrastructure conceptual architecture). Current implementation still requires production acceptance and root public-contract evidence where applicable.


## Owner-approved INF-02 access restriction — host super-administrators only (18 November 2026)

**All** Infrastructure administration screens and interactive public management interfaces—including dashboards, read-only status, logs/evidence views, reports, exports, changes, backups, restoration and time synchronisation—are restricted **exclusively to explicitly authorised host-application super-administrators**. Lower-level host administrators, tenant/group administrators and ordinary users have no access. The menu is not displayed to them, and all routes, server queries, API commands, feeds and deep links enforce the same server-side authorisation. The permission is installation/host scoped and checked against trusted IAM/Authorisation; a label, tenant parentage or client-supplied claim is insufficient. This is **not** an unrestricted “god-user” bypass or authority to inspect tenant business data (accepted ADR-0017). Critical actions still need strong/recent Authentication, independent approvals and Audit. Internal capability infrastructure ports continue unattended without super-admin user sessions. See INF-02 contract and acceptance (former review: infrastructure conceptual architecture).

### Approved installation and operational contracts (INF-01–05)

The installation/deployment contract publishes supported platform prerequisites, versioned manifests/images, network/storage and secret **names** (never values), environment/compatibility matrix, idempotent where feasible bootstrap/start/stop/upgrade/verify/recover commands, destructive exceptions, safe reruns, rollback, tested restore and provider exit. Development, acceptance and production profiles isolate secrets, stores, volumes and lifecycle; development auto-setup/credentials must not reach production. Hetzner VPS/Coolify is the current target, not a mandatory provider. Separate PostgreSQL 18 application and Temporal database lifecycles; application S3 images/files are not infrastructure backups. Infrastructure recovery must work even when application Scheduler/Workflow/MQ is down.

| Idealised input | Validation and result |
|---|---|
| ReadInfrastructureStatus; ProposeOperationalChange; ApproveOrCancelChange; ApplyOrReconcileChange | Installation-scoped authority, independent approval when required, expected revision, idempotency, desired/applied/verified versus uncertain state |
| RequestBackupRestoreOrRecovery; ConfigureTimeSynchronisation | Recovery scope, legal holds, source-owner migration/restore consistency requirements; NTP/NTS policy exclusively Infrastructure-owned |
| IngestProviderEvidence; ReadQualifiedConstraints | Trusted provider provenance, observation freshness and applicable legal/privacy/operational policy; unknown mandatory constraints hold unsafe operations |

| Idealised output | Evidence and boundary |
|---|---|
| InfrastructureReadiness; ResourceCapabilityStatus | Resource/installation, capacity, connection readiness, approved endpoint/opaque credential reference, source/age, ready/degraded/unavailable/unknown; no domain health claim |
| OperationalChangeResult | Requested/approved/applying/provider-acknowledged/verified/failed/uncertain/compensated, change/revision/actor/evidence; no blind retry |
| UtcSynchronisationStatus | Desired/applied source, authenticated trust, offset/uncertainty, source revision, freshness, holdover, leap/smear compatibility and recovery |
| BackupRecoveryEvidence | Snapshot identity, coverage, recovery-point window, integrity, verified restoration and exceptions; owner validates logical correctness |
| InfrastructureChangeCommitted; InfrastructureIncidentChanged; SanitisedOperationalSummary | Committed scoped operational facts and redacted aggregates; replay-safe, not exactly once; no credentials/private endpoints |

Host supplies trusted providers; Configuration only permitted versioned settings; Clock interprets time; Storage and Site Hosting receive provider/ingress/TLS status; Scheduler/MQ/Workflow/Gateway receive runtime prerequisites; Privacy/Legal Compliance constrain residency, retention and holds; Audit receives high-risk change/break-glass/restore evidence; Logging and Observability receive redacted diagnostics/health; Reporting and Notifications are optional consumers. Separate provider acknowledgment from independently verified outcome. No private schema access or reverse dependency on application orchestration for bootstrap.

**Standards guidance, not certified conformity:** RFC 5905/8915 NTP/NTS; RFC 3339 and IANA tzdb; NIST SP 800-53 Rev.5 and 800-34 Rev.1; CIS Controls v8.1; ASVS 5 L2/critical L3; OCI images, SPDX/CycloneDX SBOM, SLSA provenance, OpenTelemetry/OTLP, PostgreSQL WAL/PITR and WCAG 2.2 AA/BCP 47. Exact deployment RPO/RTO, sync thresholds, supported extensions, provider region, secret custody and recovery evidence remain implementation gates.

**Advisory complete-source candidates:** Docker Compose (Apache-2.0), Caddy (Apache-2.0), pgBackRest (MIT), restic (BSD-2-Clause) or Kopia (Apache-2.0; select one file backup), OpenTelemetry JS, Prometheus/node_exporter (Apache-2.0), Zod and pg (MIT), optional OPA (Apache-2.0) for deployment policy only. PostgreSQL Licence applies to database core. Verify exact release and transitive licences; OpenTofu MPL and chrony GPL are outside strict permissive library selection (system utility use separately assessed); Pulumi requires hosted-control-plane independence/exit evidence; no proprietary Terraform or duplicate Coolify control plane.

**Optional GUI:** host-owned Operations → Infrastructure dashboard, environment/resources, deployment/approval diff, backups/restores, UTC synchronisation, incidents, evidence/history; secret rotation status only. Preserve headless recovery, strong server authorisation and independent approval, accessible controls and stale/unknown display. No production use of unauthenticated template mode.

**Acceptance:** signed bootstrap produces qualified readiness; stale/replayed/revoked/self-approved change refuses or reconciles without duplicate restore; wrong-tenant/held restore fails; backup ACK without restore proof remains unknown; untrusted UTC or incompatible smear degrades/refuses; queue/Temporal outage never implies business success; offline status is stale; generic domain migration mutation unsupported. No implementation tests performed.
